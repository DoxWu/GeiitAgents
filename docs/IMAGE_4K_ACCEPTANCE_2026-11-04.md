# 4K 生图接收、保存与下载修复（2026-11-04）

## 问题与实际改动

用户反馈仅少数 4K 生图结果可以被应用接收。本轮确认代码存在与该现象一致的拒绝路径：生成图片上限为 8 MiB、模型 JSON 响应为 12 MiB，图片总预算同为 8 MiB，加密快照为 16 MiB。因此，即使模型已经生成成功，较大的 PNG 也可能在下载、Base64 响应或后续保存时失败。没有取得用户那次失败请求的原始响应，不能将此认定为现场每次失败的唯一原因。

正式修改覆盖桌面 Rust、本机浏览器直连、BYOK/服务端生图、工作室/PPT 图片校验、本机加密库和备份恢复；保留图片原始字节，不通过降低分辨率或有损重编码来绕过限制。

| 层级 | 旧上限 | 本轮上限 |
| --- | --- | --- |
| 单张生成结果 | 8 MiB | 64 MiB |
| 模型 JSON / Base64 响应 | 12 MiB | 88 MiB |
| 工作台全部图片总量（包括 PPT） | 8 MiB | 128 MiB |
| UTF-8 明文快照 | 16 MiB | 192 MiB |
| 加密备份文件 | 24 MiB | 260 MiB |
| 可请求的画布宽、高 | 512–2048 | 512–4096，16 的倍数 |
| 原生/后端结果 URL 下载总时限 | 15 秒 | 60 秒 |

前端容量常量集中到 `workbenchCapacity.ts`；对应后端和 Rust 常量保持一致。新增 3840×2160、2160×3840 和 4096×4096 预设，供应商仍需支持所请求尺寸。上传/参考原图继续保持 1,500,000 字节；对话图片输入总量、任务数量和本地知识库限制未在本轮扩大。

Base64 编解码改为小块处理，避免对整张大图执行逐字节回调和生成巨大的临时数组。保存和重新打开时检查 Base64 全文格式、字节数与文件签名，签名检查只解码头部。加密写入队列内只编码一次 UTF-8 明文，减少重复分配。

实际桌面测试还发现：锁库会先显示解锁表单，而大图的最后一次写入仍未结束；立即解锁可能读回旧内容。本轮加入锁库完成屏障，解锁等待最终写入和本机 MCP 撤权结束，重复锁库等待同一操作；画面立即锁定和在途请求取消仍保留。

- 超过64 MiB及无效签名分别显示具体错误，没有退回通用模型配置建议。

## 兼容性与验证边界

- 加密库/备份保持 v1 格式，当前代码继续读取既有数据；超过旧容量或尺寸限制的新数据不能保证被旧客户端读取。保存大图后应使用 dev.81 或更新版本读取/恢复，不能将格式号未变理解为旧版本支持扩大的容量。
- 64 MiB 单图及 128 MiB 总图量仍为有限容量；最大总量、低内存设备、物理断电和实际磁盘满未在本轮验收，不能据此承诺所有设备上的性能。
- 本轮使用合成材料与隔离 WebView2 profile，没有调用真实供应商、读取/修改 `.env`、触碰用户密钥库、发邮件、连接业务数据库或启动 Docker。没有安装日常应用、签名、发布或部署。
- 测试宿主/WebView2子树与合成HTTP服务均已退出；自动审批以策略限制拒绝了删除四个已核对路径的隔离WebView2缓存目录，因此四个 `run-*/webview` 目录暂留于 `.tools/image4k-20261104/native`。日志、报告和截图保留；没有本轮Docker镜像/容器需要清理。
- 保留不向图片 CDN 发送模型密钥、拒绝重定向、限制 URL/公网地址和验证 MIME/文件签名等下载约束。浏览器直连仍受供应商 CDN 的 CORS 策略影响。
- 既有 Office 原生版式、目标部署迁移/恢复、生产并发压测、签名更新与其他真机测试未由本轮关闭。
