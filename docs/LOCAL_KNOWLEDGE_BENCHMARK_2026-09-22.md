# 本地知识库性能与检索质量基线

日期：2026-09-22。状态：已建立可复跑的合成基准，并在当前 Windows 开发机完成两次标准规模实测。此结果用于发现瓶颈和防止后续回退，不代表 8 GB 低配设备、真实企业语料或 2000 片段上限验收。

## 基准范围

`frontend/scripts/benchmark-local-knowledge.mjs` 通过正式 Vite 构建和页面操作走完整产品路径：用户明确启用已缓存的默认 E5、选择文件、Worker 单线程 CPU/WASM 分块及向量化、IndexedDB 原子保存、页面查询和 Top 5 排序。它不直接调用内部函数，不使用聊天模型，不读取 `.env`，不发送业务 API 请求。

固定语料在 `scripts/fixtures/local-kb-benchmark.mjs`：24 份中文文档各有一个人工编写的虚构办公制度，另加无关兴趣活动文档至产品当前 100 文件上限；48 个相关性判断由每份制度的中文问题和英文跨语种问题组成。脚本启动时核对每个标注文件及证据原文确实存在。`standard` 规模生成 100 文件、334 片段、578,982 字节 UTF-8 文本和 513,024 字节 float32 原始向量。

运行命令：

```powershell
npm run build -- --outDir dist-benchmark
npx vite preview --host 127.0.0.1 --port 1423 --strictPort --outDir dist-benchmark
npm run benchmark:local-knowledge
```

基准使用 `.tools/local-knowledge-qa/browser-profile` 中此前由用户主动启用并校验完成的模型缓存，每次删除该 QA origin 的测试索引后重建。结果写入 `.tools/local-knowledge-benchmark/latest.json`，不会提交仓库。空缓存会明确失败，不会为了跑分隐式下载模型。

## 本机结果

测试设备：Windows 11 10.0.26100、AMD Ryzen AI 9 HX 370、24 逻辑处理器、29,654,634,496 字节物理内存；Playwright Chromium、Transformers.js WASM CPU 单线程、默认 `Xenova/multilingual-e5-small` q8。两轮各执行 48 个查询，共 96 次查询样本。

| 指标 | 第一次 | 有效复测 |
| --- | ---: | ---: |
| 缓存模型启用 | 2,124 ms | 1,405 ms |
| 100 文件 / 334 片段索引 | 123,056 ms | 115,090 ms |
| 每 100 片段索引 | 36,843 ms | 34,458 ms |
| 查询 P50 | 106 ms | 91 ms |
| 查询 P95 | 121 ms | 107 ms |
| 查询最大值 | 148 ms | 109 ms |
| Recall@1 | 93.75% | 93.75% |
| Recall@5 | 95.83% | 95.83% |

中文 24 问 Recall@1/5 均为 100%。英文查询纯中文资料时 Recall@1 为 87.5%、Recall@5 为 91.67%；失败项是英文差旅报销问题和英文访客胸卡问题。这个小型合成集合证明当前实现能够跨语种工作，也暴露了跨语种召回不稳定，不能外推为真实业务准确率。

有效复测以 2 秒间隔采样本轮新建的全部 `chrome-headless-shell` 进程：页面打开、模型未启用时工作集 269,996,032 字节；采样峰值 1,027,256,320 字节，峰值私有内存 862,789,632 字节；查询完成时工作集 893,808,640 字节。峰值相对页面基线增加约 722 MiB。这是浏览器、GPU/网络子进程、WASM 运行时、模型和索引的合计工作集，可能漏掉短于采样间隔的峰值，不能描述为模型独占内存。origin 总用量约 137.1 MB，包含 129.1 MiB 模型缓存、索引及浏览器开销。

两次运行均为 0 个 `/api/v1/` 请求、0 个模型网络请求和 0 个页面错误。第二次修复了首轮只匹配 `chrome.exe` 导致内存为零的采样器；首轮无效内存值不作为证据。质量结果两次完全相同，耗时受系统负载影响，应使用区间和分位数，而非单点 SLA。

## 代码优化

`rank()` 原先在每次查询中对每个持久向量重新归一化并创建新数组，之后再对全部结果排序。本批改为一次循环计算有限值、范数和点积，只保留当前 Top 5；仍拒绝维度错误、NaN、Infinity、零向量及溢出范数，并支持合法的非单位向量。这样减少查询时临时数组与全量排序，复杂度从全量 `O(n log n)` 排序降为 `O(n * 5)` Top 5 插入；本批没有优化 Worker 的串行向量化。

## 结论与剩余验收

- 当前查询在 334 片段上保持约 0.1 秒，页面交互没有出现明显阻塞；索引吞吐约每 100 片段 34–37 秒，是更明确的等待瓶颈。
- 100 文件已达到文件数量上限，但 334 片段只占 2000 片段上限约 16.7%，文本只占 10 MiB 上限约 5.5%。这次是“文件数量上限”场景，不是“最大文本/片段”场景。
- 当前设备内存约 27.6 GiB，不能替代 8 GB 无独显设备验收。还需在目标低配设备测量 1000–2000 片段、接近 10 MiB 文本、长时间索引取消/恢复和操作系统内存压力。
- Recall 集合只有 48 个合成问题。下一轮质量工作应引入脱敏真实样本、同义改写、短查询、跨语种和 hard negative；在证据支持前不调整默认模型。
- 后续性能优化优先评估小批量 embedding 与可恢复索引检查点；批量大小必须以 8 GB 峰值内存为约束。近似向量索引在当前规模和约 0.1 秒查询下不是首要瓶颈。
