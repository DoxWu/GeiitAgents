# 发布与 Schema 安全操作说明

本文为发布前检查清单，依据当前仓库的应用角色、Alembic 迁移和备份接口整理。它不是已演练的 staging/生产 runbook，也不授权或执行线上变更。上线前须由目标环境负责人补齐平台、镜像、流量切换、备份位置和恢复权限。

## 发布前

- 记录当前应用镜像不可变标识、当前 Alembic revision、配置版本和回退责任人。不要依赖可变的 `latest` 标签。
- 对目标数据库和 `/app/uploads`、`/app/data` 生成一致性备份，并在隔离环境完成恢复、登录、文档预览、问答检索和待办/提醒检查。只看到备份文件存在不算恢复验证。
- 检查本次迁移 SQL、锁和索引构建成本、PostgreSQL/pgvector 兼容性、Worker/Beat 任务兼容性及资源/维护窗口。
- 在隔离 staging 部署相同镜像和迁移。确认健康检查、登录、上传处理、删除/导出、检索、SSE、提醒调度、队列积压和关键告警。
- 若平台支持流量权重，可先让小比例流量进入候选版本；若不支持，使用独立测试服务，不要把复制生产数据库的副本接到外部邮件或模型供应商。

## Schema 迁移

采用 expand/contract 的多次发布方式：

1. 先增加向后兼容的表、列或索引，保留旧字段与旧读写路径。为大表索引评估 PostgreSQL 并发创建与迁移事务限制。
2. 在备份和 staging 恢复验证后发布兼容新旧 schema 的应用，执行受监控的数据回填并校验行数、约束、索引和应用查询。
3. 单独发布切换读写的版本；观察错误率、查询延迟和后台队列。保留旧镜像仍可读写的兼容窗口。
4. 只有回退窗口关闭且备份恢复再次确认后，才在后续发布中删除旧字段或表。

不要把 `alembic downgrade` 当作通用回滚。若 downgrade 会删除数据、列、索引或约束，先停止发布并选择兼容应用镜像、前向修复迁移，或在隔离环境还原后由负责人决定数据恢复方案。禁止在唯一生产库上试跑未知 downgrade。

## 回退与停止条件

- 出现登录/权限错误、数据完整性问题、迁移阻塞、检索空间不匹配、队列持续增长或错误率越线时，停止扩大流量并保留日志、镜像标识和迁移 revision。
- 若 schema 仍兼容，回退应用镜像并确认 API、Worker、Beat 使用兼容版本；Beat 对同一数据库/队列只运行一个活动实例。
- 若 schema 已不兼容，不要盲目回退应用。暂停不兼容写入，按 staging 验证过的前向修复或隔离恢复方案处理，并确认上传文件和数据库快照属于同一时间点。
- 恢复后核对用户数、文档/分块数量、文件校验和、检索结果、未完成任务与提醒状态，再决定是否恢复流量。

## 当前验证边界

仓库模板和本地隔离测试不代表目标平台灰度、镜像回退、RWO 卷切换、备份恢复或迁移耗时已经演练。本轮没有访问线上资源，也没有执行数据库 downgrade、部署或真实供应商投递。目标环境演练结果、RPO/RTO、维护窗口与责任人仍需部署方确认。
